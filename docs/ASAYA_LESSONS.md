## Предлагаемый способ исполнения

Следующие пункты — практический перевод этого опыта в процесс «ДВУХ КОРОБОК», а не дословные прежние инструкции пользователя.

1. **Проверять исходную точку.** Перед изменениями установить репозиторий, ветку, коммит, незавершённые правки и нужный макет. Использовать источники из `AGENTS.md`: `docs/FIGMA_HANDOFF.md`, `content/business.json`, `content/pages.json` и `docs/ASSETS_MANIFEST.md`. Не начинать новую реализацию из-за пустого чата.

2. **Сохранять короткую точку продолжения.** До существенной работы записать текущее состояние и ближайшую задачу. После законченного этапа обновить принятые решения, выполненное, оставшиеся вопросы и следующий конкретный шаг. Важные сведения должны жить рядом с кодом; длинная переписка не заменяет такую запись.

3. **Вести один набор исходников.** Править исходный контент и шаблоны, получать результат штатной сборкой. Не редактировать `dist/` вручную. Архив и отдельный HTML-просмотр не становятся новой основной версией сайта. GitHub, локальная папка и preview должны иметь понятную связь с коммитом.

4. **Разделять состояния результата.** В отчёте отмечать: подготовлено в коде, проверено автоматически, проверено визуально, доступно в preview, опубликовано, проверено на рабочем адресе. Не писать «уже работает на сайте», если подтверждён только PR или сборка. Сохранять идентификатор опубликованной версии и понятный способ возврата к предыдущей.

5. **Проверять именно затронутое поведение.** Выполнять обязательный `npm run check`. Визуально сверять изменённые страницы с согласованными кадрами на ширинах 390 и 1440 px: кадрирование, текст, меню, кнопки, переполнение. Для формы обращений отдельно проверять её реальное завершение, если она реализована. Успешная сборка не подтверждает доставку заявки. Результаты разных прогонов не складывать в один показатель.

6. **Сохранять единые данные.** Контакты, адреса, цены и гарантии брать из предусмотренных файлов контента. Неподтверждённые значения оставлять открытыми вопросами, не заполнять правдоподобными догадками. Для изображений фиксировать происхождение и назначение; подпись конкретной модели коробки требует подтверждения.

7. **Работать завершёнными этапами.** Сначала заканчивать согласованную правку интерфейса, затем переходить к следующей. Не перечитывать всю историю без необходимости. Кратко сообщать результат, проверку, оставшийся риск и следующий шаг. Обрыв соединения или лимит не должен заставлять восстанавливать весь проект заново.

## Что не переносится автоматически

Нынешняя задача — статический сайт специализированного автосервиса. Магазин, корзина, кабинет, SMS-вход, платежи, склад, доставка, вебхуки, PostgreSQL и серверная архитектура ASAYA не становятся требованиями «ДВУХ КОРОБОК». Добавлять их можно только под конкретную подтверждённую потребность.

Если понадобится внешняя интеграция, сначала определить её пользовательскую задачу и проверить актуальную официальную документацию. Подключённый аккаунт или установленный модуль ещё не подтверждают рабочую интеграцию: нужен проверенный результат на реальном маршруте пользователя.
